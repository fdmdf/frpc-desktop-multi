## 关键设计取舍

### 1. 引擎放在 jniLibs（而不是 assets 拷贝到 filesDir）

Android 10+ 禁止从应用数据目录 `execve`（W^X）。1.0.0 把二进制拷到 `filesDir/bin` 后真机直接 `error=13 Permission denied`。

jniLibs 是系统认可的 native 库落点：安装时解压到 `/data/app/.../lib/arm64/`，进程可直接执行。代价是必须命名为 `lib*.so`，且需要 `extractNativeLibs=true`。

### 2. 代理状态「双源」

| 来源 | 优点 | 缺点 |
| --- | --- | --- |
| 状态接口 `webServer`（`/api/status`） | 精确状态、实际分配端口、错误原因 | 需开启；明文 HTTP 需放行回环 |
| 日志推断（`proxy added` / `start proxy success` / `start error`） | 无需额外配置，一定有 | 拿不到实际端口，控制连接断开时状态清空 |

实现上先取接口数据，缺失时用日志推断，两者都没有时显示「未知」而不是「离线」——避免误导。

### 3. TOML 编解码的两个坑

- **ktoml 0.7.1 缺陷**：`[[proxies]]` 内的点分键（`transport.x = y`）会为每个键生成一个同名子表，导致解码丢字段。`FrpcToml.decode` 解析后合并同名子表修复。
- **frp 按类型严格解码**：例如 sudp 带 `remotePort` 会让 frpc 直接退出。导入和切换代理类型时调用 `ProxyConfig.sanitizedForType()` 清理，校验器再兜一层。

### 4. 前台服务 + 单例 Supervisor

- `FrpcSupervisor` 是进程级单例：持有子进程、日志环形缓冲、状态/资源 Flow，UI 与 Service 都只读它
- `FrpcService` 只做两件事：维持前台通知、把停止/重载动作转给 Supervisor
- 崩溃重启用指数退避（2s → 60s，最多 5 次），避免「启动-崩溃」死循环耗电

### 5. 不做的事

- 不引入 Room/KSP、导航库、DI 框架：数据量小（几十条配置），JSON 文件 + 手写返回栈 + 懒加载容器已足够，换来更小的包体与更快的构建
- 不在 UI 层直接做 IO：UI 只收集 Flow，写操作走 Repository/Store

## 测试策略

| 层次 | 位置 | 覆盖 |
| --- | --- | --- |
| 纯逻辑 | `shared/src/commonTest` | TOML 往返、真实 frp 配置解析、校验规则、类型字段兼容 |
| JVM 相关 | `shared/src/jvmCommonTest` | 状态接口客户端（本地 HttpServer 集成测试）、/proc 采样 |
| 应用层 | `androidApp/src/test` | 编辑器草稿守卫、日志解析、代理状态推断 |

`commonTest` 两个平台都会跑（`jvmTest` 与 `testDebugUnitTest`），保证双端行为一致。

## 引擎构建

`scripts/build-frpc.sh`：拉取 frp 源码 → 准备 Web 控制台产物 → `CGO_ENABLED=0 GOOS=android GOARCH=arm64 go build -tags frpc` → 输出 `libfrpc.so` + `VERSION`。CI 会定期执行一遍验证可复现性。
