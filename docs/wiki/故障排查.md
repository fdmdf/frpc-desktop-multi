# 故障排查

按现象查找。每条都给出判断依据与处理方式。

## 启动失败：`error=13, Permission denied`

**现象**：日志出现 `Cannot run program ".../libfrpc.so": error=13, Permission denied`。

**原因**：Android 10+ 禁止从应用数据目录执行二进制。1.0.1 起引擎改为以 `libfrpc.so` 随 jniLibs 分发，安装时由系统解压到 `nativeLibraryDir` 执行。

**处理**：

1. 确认版本 ≥ 1.0.1（设置 → 关于）
2. 若仍报错，说明安装未解压 native 库：卸载后重新安装
3. 若日志中的路径是 `/data/user/0/.../files/bin/frpc`，说明跑的是**旧版**，请安装新版

## 状态一直「未知」或「离线」，但日志显示 start proxy success

**原因**：未开启「状态监控（本机接口）」，或 App 访问状态接口失败。

**判断**：

- 日志里是否有 `admin server listen on 127.0.0.1:7400`
- 主页是否提示「状态监控接口无响应」

**处理**：

1. 配置中开启「启用状态监控（本机接口）」
2. 检查端口是否被占用（7400 可能冲突，换一个）
3. 1.0.6 起已修复 Android 明文 HTTP 拦截问题；更低版本请升级
4. 即使不开启，App 也会用日志推断状态（在线/异常），只是拿不到实际随机端口

## CPU / 内存显示 `--`

1.0.5 起已修复（进程名匹配问题）。更低版本请升级。若升级后仍为空：

- 确认处于「运行中」状态
- 设备为 32 位时无法运行引擎（见下）

## `connect: connection refused` / `i/o timeout`

| 报错 | 含义 |
| --- | --- |
| `connection refused` | 服务端端口没监听（frps 未启动 / 端口写错 / 防火墙拒绝） |
| `i/o timeout` | 网络不通或丢包（服务器不可达、运营商屏蔽、kcp 端口不匹配） |

**处理**：

1. 确认 frps 正在运行且端口可达：在别的机器上 `telnet frps地址 7000`
2. 使用 kcp / quic 时，确认服务端监听端口与 App 里填的端口**完全一致**（见 [协议兼容性](协议兼容性.md)）
3. 云服务器记得放行安全组 / 防火墙

## `login to server failed: token mismatch` 之类

Token 与服务端 `auth.token` 不一致。注意首尾空格。

## 代理显示「异常：proxy [x] already exists」

同一个代理名在服务端已注册（常见于上一次客户端未正常断开）。等几秒后重试，或改名。

## 代理显示「异常：requires vhost_http_port / tcpmux_httpconnect_port」

服务端缺少对应端口配置。https 代理还需要本地服务本身支持 HTTPS（TLS 透传）。

## 浏览器打开远端端口显示 `Host check error` / `Invalid Host header`

**先确认这页是谁返回的**：frp 本身没有这个提示（`frp v0.71.1` 源码里搜不到这个字符串），
页面来自你隧道指向的那个内网服务。

10 秒验证（在跑服务的机器上执行，把 `<本地端口>` 换成代理里填的 localPort）：

```bash
curl -i -H "Host: 192.168.0.5:54408" http://127.0.0.1:<本地端口>/
```

如果这里也返回同样的页面，就是后端在拒绝 Host 头，与 frp 无关。

常见于这些服务：webpack / Vite dev server、Django、ASP.NET、各类管理面板、NAS 管理页——
它们只允许「设定过的域名」访问，防止 DNS rebinding。

三种处理方式：

1. **改用 HTTP 代理**（推荐给网页服务）：类型选 `http`，`customDomains` 填一个域名，
   在「Host 头重写」里填后端认的域名（如 `nas.local`），frps 会把 Host 改成它再转发
2. 在服务端把访问地址加入白名单（Django 的 `ALLOWED_HOSTS`、webpack 的 `allowedHosts`、
   Vite 的 `server.allowedHosts`）
3. 直接访问后端认的域名（把该域名解析到 frps 所在 IP）

> TCP / UDP 代理是**原样转发**，frp 无法修改 Host 头，这类服务只能走上面的 1 或 2。

## 32 位设备无法使用

引擎仅提供 **arm64-v8a**（Go 对 android/arm 32 位不支持纯静态链接，上游 frp 同样只发 arm64）。设置 → frpc 引擎 会显示「未找到适用于当前设备的引擎」。

## kcp 连不上但 tcp 正常

90% 是端口没对齐：frpc 用 kcp 时拨的是 `serverAddr:serverPort`，服务端 `kcpBindPort` 必须与之一致。其次是 UDP 被网络中间设备拦截（部分运营商/公司网络）。

## xtcp 访问者报 `nathole exchange info error: get natHoleRespMsg error: context deadline exceeded`

这条日志的意思是：**你这一侧 STUN 探测成功了，但对方（提供 xtcp 代理的那台 frpc）没有在超时内回应打洞请求**。按顺序排查：

1. **对方 frpc 在不在线**：对方主页应显示「运行中」且 `login to server success`；xtcp 代理应出现 `start proxy success`
2. **代理名与密钥**：访问者的「对方代理名」必须和对方的代理名完全一致；私密密钥两边必须相同
3. **跨设备前缀**：对方的代理名带了 user 前缀时，访问者要填「对方设备前缀」（对应 `serverUser`），且对方代理的「允许访问的账号」要包含你的前缀，或直接填 `*` 放行所有 user（frp 支持该通配）。代理名本身不要再带点，否则会被再拼一次前缀
4. **对方 STUN 连不上（最常见）**：对方日志若出现 `nathole prepare error: discover error: wait response from stun server timeout`，说明它做不了 STUN 探测、**根本没回应你**，于是你这边干等到超时。让对方在配置里填「STUN 服务器」，例如 `stun.miwifi.com:3478`
5. **双方都是 HardNAT**：日志里 `nat type: HardNAT, behavior: BehaviorPortChanged` 说明端口会被运营商改写（蜂窝网络几乎都是）。**两边都是 HardNAT 时 UDP 打洞基本不可能成功**——这不是 App 或 frp 的问题，让其中一方换到普通家庭宽带（多数为 EasyNAT）再试

**注意因果是反的**：访问者侧报 `deadline exceeded`，根因常常在**提供代理的那一边**（它 prepare 失败所以没回话）。先看对方的日志，别只盯着访问者。

**默认 STUN 很不稳定**：不填 `natHoleStunServer` 时 frpc 用 `stun.easyvoip.com:3478`，实测三次探测常只成功一次（且延迟 500ms+）；换成 `stun.miwifi.com:3478` 或 `stun.chat.bilibili.com:3478` 基本 3/3 命中、延迟 50ms 左右。**只要用了 xtcp，就把这一项填上**（App 会在校验里给警告）。注意手机和电脑要各填各的，两端都得能连上 STUN。

**装了系统代理 / 虚拟网卡（TUN）的机器**：打洞日志里的 `assistedAddresses` 是**本机各网卡的 IP**（frp 用 `ListLocalIPsForNatHole` 收集，只在双方同一局域网内有用）。若里面出现 `198.18.0.x` 这类虚拟网卡地址，说明 UDP 被虚拟网卡接管，即使日志显示 `establishing nat hole connection successful`，数据面也可能不通。临时关掉系统代理或退出该软件再试。

### 让 xtcp 打不通也能用：fallbackTo

xtcp 的兜底是**再建一条 stcp 访问者指向同一个代理**，然后在 xtcp 访问者里把「打洞失败转交给」（`fallbackTo`）填成那个 stcp 访问者的名字。frp 在打洞超时（`fallbackTimeoutMs`，默认 1000ms）后会把连接转交给它，数据改走 frps 中转——能用，只是多一跳、占服务器带宽。

两端都在访问者编辑页、类型为 XTCP 时可以填这两个字段。

### 不想用第三方 STUN

frp 没有自带 STUN 服务端（`NatHoleSTUNServer` 只是客户端配置，默认 `stun.easyvoip.com:3478`），frps 也不提供地址观测。STUN 只回一句话「你的公网地址是 X」，业务数据一字节都不经过它，风险主要是**可用性**而不是隐私。

要完全自建：在跑 frps 的那台 VPS 上装 coturn，只开 STUN（`listening-port=3478`，不开 relay/认证），然后两端 `natHoleStunServer` 都填 `你的VPS:3478`。注意它和 frps 是两个独立进程 / 端口，frps 不会替你做这件事。

## 后台一会儿就被杀

1. 设置 → 「忽略电池优化」→ 去设置，把 App 加入白名单
2. 小米/华为等机型还需在系统设置里允许「自启动」「后台活动」
3. 确认前台服务通知一直存在（被清理后服务可能被回收）

## 开机自启没生效

- 设置 → 开机自启 已开启，且设置了「默认配置」
- 部分系统（Android 12+）限制开机后台启动前台服务，若失败 App 会弹通知提示手动打开

## 手机浏览器打开 `127.0.0.1:7400` 是空白页 / 404

- 正确地址是 `http://127.0.0.1:7400/static/`（访问 `/` 会 301 跳转）
- 需要输入配置里的状态监控用户名/密码（默认 `admin/admin`）
- 1.0.8 起已内置官方 Web 控制台；更低版本只有占位页

## 日志里每 2 秒刷一条 `http request`

不是故障。App 每 4 秒调用一次 `127.0.0.1:7400/api/status` 读取在线状态，frpc 的 `NewRequestLogger`
会为每个请求固定打两行（`http request: [...]` 与 `http response [...]`），看起来像每 2 秒一条。

- 1.0.10 起默认在界面隐藏这两行，可在 **设置 → 日志 → 显示状态接口访问日志** 打开
- 想彻底不产生这两种日志，只能关闭配置里的「状态监控」——但那样 App 就只能按日志推断代理状态，
  拿不到真实端口与在线代理数，不建议
